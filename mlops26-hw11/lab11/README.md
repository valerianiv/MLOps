# ДЗ 11. Kubernetes под нагрузкой

Работа посвящена развёртыванию API в Kubernetes, проверке прогрева и обновления реплик, сравнению политик балансировки, настройке мониторинга и HPA.

Используется **CPU-имитатор**, который явно возвращает `backend_mode=simulated`. Части ответа не являются токенами языковой модели, поэтому задержки называются **TTFC** и **inter-chunk latency**.

Код и сохранённые результаты находятся в [репозитории MLOps](https://github.com/valerianiv/MLOps/tree/main/mlops26-hw11/lab11). Коммит сдаваемой версии необходимо указать в итоговом отчёте.

## Выполненные эксперименты

### A. Прогрев, обновление и откат

- Воспроизведена ошибочная готовность HTTP-процесса до завершения прогрева backend.
- Исправлены startup/readiness probes.
- Выполнено обновление A → B под нагрузкой с длительным потоковым ответом.
- Проверено исключение заведомо неготовой реплики из рабочих EndpointSlice.
- Выполнен управляемый возврат к версии A.
- Отдельно выполнено аварийное завершение процесса с фиксацией оборванного ответа и восстановления обслуживания.

В исходном rollout завершились 97 из 100 запросов, три были отклонены по тайм-ауту очереди. После изменения тайм-аута очереди с 30 до 65 секунд завершились **100 из 100 запросов**.

Увеличение тайм-аута устранило отказы при данной нагрузке, но не увеличило вычислительную ёмкость сервиса.

### B. Привязка клиента и горячая реплика

Сравниваются два Service над двумя репликами:

- `api` — без привязки клиента;
- `api-sticky` — с `sessionAffinity: ClientIP`.

Используются четыре клиентских Pod с разными IP. Для каждой политики выполнены равномерный и горячий сценарии: **три повтора по 120 секунд**. В горячем сценарии один клиент отправляет 80% запросов.

Для сравниваемых политик сохранены одинаковые расписания, входы и ограничения ответов. Перед прогонами реплики заменяются, backend прогревается, локальный кеш начинает работу пустым. Каждый запрос использует отдельное соединение.

При горячем клиенте:

| Политика | p95 TTFC по трём повторам | Доля неуспешных запросов |
|---|---:|---:|
| Обычный Service | 1,38–2,00 с | 0% |
| ClientIP | 9,52–9,55 с | 26–33% |

В первом горячем прогоне ClientIP распределил 624 запроса на одну реплику и 96 на другую. Среднее ожидание очереди у успешных ответов составило около 8,58 и 0,03 секунды соответственно.

Сохранён и результат без перекоса: в `uniform-api-sticky-1` запросы распределились поровну — 360/360. Во втором равномерном прогоне ClientIP распределение составило 540/180. Это показывает зависимость результата от назначения клиентов репликам.

Для данного горячего сценария выбран обычный Service. Вывод относится к модели нагрузки CPU-имитатора; для настоящего inference engine требуется отдельная проверка кеша, batching и стоимости пересчёта контекста.

### C. HPA и алерты

Настроен HPA `autoscaling/v2`:

- минимум — 2 реплики;
- максимум — 3 реплики;
- целевая CPU utilization — 55%;
- CPU request приложения — 200m;
- окно стабилизации уменьшения — 60 секунд.

Сохранены результаты масштабирования **2 → 3 → 2**, условия HPA и данные resource metrics API. После завершения нагрузки наблюдаемое ожидание возврата к двум репликам составило около 89 секунд.

Настроены два алерта:

| Алерт | Условие | Удержание |
|---|---|---|
| `LabHighTTFC` | p95 TTFC > 0,8 с при минимум 10 завершениях за минуту | 20 с |
| `LabRefusals` | Доля неуспешных исходов > 5% при минимум 20 исходах за минуту | 20 с |

В сохранённых результатах подтверждены состояния `pending`, `firing` и последующее восстановление для обоих правил. При отсутствии нагрузки состояние `Inactive` нормально.

## Проверки

В сохранённых результатах Kubernetes-опытов — **15 успешных проверок из 15**.

Они включают:

- недоступность непрогретого backend;
- сохранение версии и SHA-256 артефакта после замены Pod;
- фактически загруженную версию после отката;
- изоляцию диалогов с различимыми контрольными строками;
- раздельный учёт отказов и незавершённых потоков;
- штатный rollout без потерянных ответов;
- восстановление после аварийного завершения процесса;
- масштабирование и переходы алертов.

Дополнительно предусмотрены восемь локальных HTTP-проверок приложения и генератора. Они не заменяют Kubernetes-эксперименты.

## Требования к окружению

Команды выполняются в Linux. В Windows используется WSL2, например Debian:

```powershell
wsl -d Debian
```

Docker Engine должен быть запущен и доступен из WSL:

```bash
docker version
df -h .
```

Ориентир для локального стенда — 4 CPU, 8 ГБ RAM и 12–15 ГБ свободного места. Это рекомендуемый запас, а не измеренный размер стенда.

Закреплённые версии инструментов:

- kind 0.27.0;
- Kubernetes / kubectl 1.32.2;
- Helm 3.17.2;
- metrics-server 0.7.2.

Python-зависимости закреплены с хешами в `requirements.lock`. Версии образов указаны в Dockerfile и конфигурациях; фактические сведения об окружении сохранены в `evidence/`.

Prometheus ограничен хранением метрик в течение 6 часов и размером TSDB 384 MB. Его временный том ограничен 512 MiB, том Grafana — 128 MiB.

## Повтор экспериментов

Фазы изменяют один стенд и должны выполняться последовательно.

Каталоги `results/A`, `results/B`, `results/C` и `results/checks` уже содержат результаты. Перед повторным запуском сохраните существующую `results/` под другим именем. Скрипты не предназначены для перезаписи готовых фаз.

Локальные проверки:

```bash
.venv/bin/python -m unittest discover -s tests -v
```

Полный цикл:

```bash
set -o pipefail
bash scripts/lab.sh all 2>&1 | tee run.log
```

Либо отдельные фазы:

```bash
bash scripts/lab.sh check
bash scripts/lab.sh a
bash scripts/lab.sh b
bash scripts/lab.sh c
bash scripts/lab.sh inventory
bash scripts/lab.sh report
```

Результаты проверок сохраняются в `results/*/checks.jsonl`. Завершение скрипта само по себе не заменяет проверку исходов запросов и PASS/FAIL.

Генерация отчёта может перезаписать ручные изменения `report.html`. Перед запуском сохраните копию отредактированного отчёта.

## Демонстрация API

В отдельном терминале:

```bash
kubectl --context kind-mlops-lab11 -n lab11 port-forward svc/api 18091:8080
```

В другом терминале отправьте запрос:

```bash
curl -iN http://localhost:18091/stream --json '{"prompt":"Stream test","chunks":4,"chunk_delay":0.475}'
```

Ожидаются четыре записи `chunk` и завершающая запись `done`. Ответ содержит request ID, Pod, версию, SHA-256 артефакта и `backend_mode=simulated`.

Потоковый маршрут — `/stream`. Параметр `chunk_delay` задаётся в секундах. Маршрут `/generate` возвращает один итоговый JSON.

`port-forward svc/api` направляет запросы в один выбранный Pod. Для сравнения балансировки используются клиентские Pod и ClusterIP Service в опыте B.

## Grafana

В отдельном терминале:

```bash
kubectl --context kind-mlops-lab11 -n lab11 port-forward svc/grafana 3000:3000
```

Откройте **http://localhost:3000**, дашборд **Lab11 — CPU simulated backend**.

Панели показывают:

- p95 TTFC и полную длительность ответа;
- running/waiting по Pod;
- завершённые и неуспешные запросы в секунду;
- CPU и RAM по Pod;
- число Ready-реплик;
- попадания и промахи имитируемого префиксного кеша.

Выберите период фактической нагрузки. Без завершённых запросов перцентиль может отсутствовать. Метрики старых опытов могут быть недоступны после истечения срока хранения или удаления Prometheus.

Сохранённые графики остаются в `results/figures/` и доступны через `report.html`.

## Prometheus

В отдельном терминале:

```bash
kubectl --context kind-mlops-lab11 -n lab11 port-forward svc/prometheus 19090:9090
```

Откройте **http://localhost:19090**.

На странице **Status → Targets** проверьте группы:

- `api` — метрики каждой реплики приложения;
- `kube-state` — состояние объектов Kubernetes;
- `cadvisor` — использование CPU/RAM контейнерами.

При двух репликах приложения в группе `api` ожидаются два адреса со статусом `UP`.

На странице **Alerts** доступны `LabHighTTFC` и `LabRefusals`. Правила заданы в Prometheus и не требуют создания аналогичных правил в Grafana.

Не держите ручное перенаправление порта 19090 во время повторного запуска экспериментов: наблюдатель опытов использует этот же порт.

## Измерения

Клиент измеряет длительности монотонными часами. Для каждого запроса сохраняются расписание и фактическая отправка, длительность, TTFC, статус, исход, Pod, версия и число частей ответа.

Раздельно учитываются завершённые, отклонённые, оборванные, просроченные, неотправленные запросы и транспортные ошибки. Перцентили рассчитываются для успешных завершений с указанием числа наблюдений.

Пример PromQL для p95 TTFC по Pod:

```promql
histogram_quantile(
  0.95,
  sum by (le, pod) (
    rate(lab_ttfc_seconds_bucket[1m])
  )
)
```

Команда сверки с клиентом при доступных метриках Prometheus:

```bash
.venv/bin/python -m tools.reconcile results/B/hot-api-1
```

Histogram даёт приближённый перцентиль, а `increase()` экстраполирует значения к границам интервала. Поэтому оценка количества наблюдений может быть дробной. Совпадение набора событий требует проверки временных границ, Pod и серверных журналов.

## Ответ на вопрос защиты

Ревью находится в `REVIEW.md` и `report.html`.

При очереди A в 3 секунды и пересчёте на свободной B за 0,8 секунды новый запрос предлагается направить на B после проверки готовности и доступной ёмкости. История диалога передаётся клиентом или хранится вне Pod. Уже начатый поток при штатном обновлении завершается на прежней реплике.

Вывод связан с кейсом Google Cloud о Vertex AI и GKE Inference Gateway. Ссылка на первичный источник приведена в HTML-отчёте:

[How GKE Inference Gateway improved latency for Vertex AI](https://cloud.google.com/blog/products/containers-kubernetes/how-gke-inference-gateway-improved-latency-for-vertex-ai).

## Ограничения

- Результаты относятся к CPU-имитатору, а не к настоящей языковой модели.
- Префиксный кеш имитирует стоимость hit/miss и не является KV-cache inference engine.
- Небольшая демонстрационная нагрузка не заменяет опыты балансировки, HPA и алертов.
- Аварийное завершение выполнено через `os._exit(137)` и рассматривается отдельно от штатного rollout.
- В `evidence/final-inventory.json` сохранена ошибка расчёта Docker disk usage. Фактический размер стенда требует дополнительного успешного замера либо отдельной обоснованной оценки.

## Удаление стенда

Сначала сохраните результаты и остановите ручные `port-forward` сочетанием Ctrl+C.

```bash
bash scripts/lab.sh cleanup
```

Команда удаляет учебный кластер kind `mlops-lab11` и его тома. Файлы результатов остаются.

При необходимости отдельно удалите образ приложения:

```bash
docker image rm lab11-api:1.0.0
```

Базовые образы и кеш сборки могут остаться. Глобальный `docker system prune` для удаления этого стенда не требуется.
