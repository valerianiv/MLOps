# Разбор дефектов части A

Каждый раздел: в чём был дефект, как проявлялся, как исправлен и каким
наблюдением/числом подтверждается. Числа — из моего прогона: sweep
`2b1ef4f21ba942c4b48b9a574307e6b0`, `make check-storage`, `make check` — 9/9,
отпечаток `tests/` `c42ac7788026`.

## 1. Все кандидаты sweep писались в один дочерний run

**Где:** `src/sweep.py`, `main()` и `run_candidate()`.

**В чём был.** Внутри родительского run `sweep` открывался ОДИН вложенный run
`all-candidates`, и все шесть конфигураций обучались внутри него. Вдобавок
`log_params` был обёрнут в `if not ...data.params`: параметры логировал только
первый кандидат, остальные молча пропускались (MLflow запрещает менять уже
записанный param, и условие маскировало это).

**Как проявлялось.** В UI под `sweep` был один дочерний run вместо шести;
кривые `val_loss` шести кандидатов накладывались на одни и те же шаги одной
метрики; params `r / lr / target_modules` соответствовали только первому
кандидату (`qv-r4-low`), тег `candidate` перезаписывался последним.
`check.py` №1 падал: «отдельных кандидатов: 1», №3 — «неверный r».

**Как исправлено.** Для каждого кандидата открывается свой
`mlflow.start_run(run_name=candidate["name"], nested=True)` прямо под `sweep`;
`log_params` вызывается безусловно — в свежем run параметров ещё нет, и
каждый кандидат пишет только свои.

**Подтверждение.** В эксперименте `hw6-lora` под `sweep` 6 дочерних run с
`tags.kind = candidate`, у каждого свои `r`, `lr`, `target_modules`, 4 точки
`train_loss` и своя кривая `val_loss` (например, `qv-r4-low`: 2.2733 → 2.2613 →
2.2472; `all-r8-high`: 2.2733 → … → 2.0299); `check.py` №1 и №3 — PASS.

## 2. Артефакты MLflow не переживали пересоздание контейнера

**Где:** `compose.yaml`, сервис `mlflow`.

**В чём был.** Сервер запущен с `--artifacts-destination=/mlartifacts`, а
volume `artifacts` объявлен в корне файла, но к сервису не подключён. Файлы
моделей лежали в записываемом слое контейнера. Метаданные run при этом
оставались в Postgres (у `db` volume подключён), поэтому run «есть», а его
файлов уже нет.

**Как проявлялось.** После `docker compose up --force-recreate mlflow`
(или `make down && make up` после пересборки образа) run открывался в UI, но
загрузка `model/` и `samples.json` давала 404/«not found»;
`make check-storage` завершался «Артефакт потерян».

**Как исправлено.** В сервис `mlflow` добавлено
`volumes: - artifacts:/mlartifacts` — путь совпадает с `--artifacts-destination`.

**Подтверждение.** `make check-storage`: «PASS: новый контейнер вернул тот же
артефакт, SHA256 совпал»; run `storage-probe` в MLflow, в
`metrics/storage-check.json` — sha256 артефакта и `compose_sha256` текущего
`compose.yaml`; `check.py` №8 — PASS.

## 3. В происхождение run не попадали версии данных

**Где:** `src/sweep.py`, `main()`:
`versions = {k: v for k, v in provenance(p).items() if not k.startswith("data_")}`.

**В чём был.** `provenance()` считает `data_train_sha256` и `data_val_sha256`
(SHA256 тензоров `train.pt` / `val.pt`), но фильтр выбрасывал все ключи с
префиксом `data_`. В тегах оставались код, конфиг и git sha — без данных.

**Как проявлялось.** По run нельзя доказать, на каких данных обучен адаптер:
после пересборки `train.pt` старый run выглядел «актуальным».
`check.py` №2 падал: «нет актуального data_train_sha256»; `make candidate`
(`promote.select`) отказывал: «отсутствует или устарел data_train_sha256».

**Как исправлено.** `versions = provenance(p)` — теги run содержат все шесть
ключей происхождения, включая хеши данных.

**Подтверждение.** У каждого кандидата теги `data_train_sha256` =
`c033c65440bb…` и `data_val_sha256` = `9d9672f76d56…` — совпадают с
`sha256sum data/tokenized/train.pt` / `val.pt`; `check.py` №2 — PASS.

## 4. Порог качества не проверялся перед регистрацией модели

**Где:** `src/promote.py`, `promote()`.

**В чём был.** Функция `gate()` с проверкой порога, конечности метрик и статуса
run существовала, но `promote()` её не вызывал: отношение
`final_val_loss / base_val_loss` считалось вручную и только записывалось в тег,
после чего модель безусловно регистрировалась, получала тег
`validation=passed` и alias.

**Как проявлялось.** Любой кандидат, даже хуже базы (ratio > 1) или с NaN loss,
попадал в реестр с `validation=passed`. `check.py` №6 падал: «кандидат с
положительным loss прошёл нулевой порог» (порог 0.0 недостижим, но версия
создавалась).

**Как исправлено.** `ratio = gate(run, threshold)` — первой строкой, ДО
`mlflow.register_model`. При отказе `gate()` бросает `ValueError`, и реестр
не меняется.

**Подтверждение.** `check.py` №6 — PASS (порог 0.0 → `ValueError`, версия не
создана); у зарегистрированной версии `my-qwen-adapter/1` (`all-r8-high`) тег
`val_ratio` = 2.0299 / 2.2733 ≈ 0.893 ≤ `max_val_ratio` 1.0.
