3. Граф задач (flow.py, flow model-release)
  prepare-input → fetch-artifact → evaluate-gate → publish-release
Между задачами передаются пути, ID и хеши; веса и тензоры не передаются.
prepare-input: схема golden/behavioral и токенизация шаблоном оценки. Вход файл и настройки,
  выход число строк, максимальная длина, хеши. Результат хранится на диске (persist_result).
fetch-artifact: чтение готового артефакта, это не обучение. База берётся из снимка HF,
  adapter из MLflow. Хеши сверяются с model-pins.json, чтобы файлы не сверялись сами с собой.
evaluate-gate: вызов исходных score/current_reports/quality_gate ДЗ 6+7 (hw67_bridge.py).
  Отчёт сохраняется при любом решении, затем validate_release.
publish-release: архив решения → атомарная замена accepted.json → журнал publications.jsonl.
Ключ кеша: SHA-256 от {data_sha256, config}. В config: ревизия токенизатора, шаблон, max_length,
версия кода подготовки, для реального потока также хеши behavioral и system.
Идентичность результата задаётся этим ключом. Идентичность попытки — flow run ID в attempts.jsonl.
Идентификатор выпуска: модель, runtime, хеши протокола и golden, evaluation_run_id, хеш отчёта.
Хранение: JSON-указатель и JSONL-журнал. Для одного писателя этого достаточно, база не нужна.
Повторяются только OSError в fetch-artifact, до 3 попыток: evidence/real/release-mlflow-down.log.
Не повторяются неверная схема, несовпавшие хеши, отказ gate: release-pins-mismatch.log.

Ответ приходит единым JSON, поэтому измерена полная задержка. TTFT и ITL не измерялись.
Prefill прогоняет весь вход и наполняет KV-cache, стоимость растёт с длиной входа. Decode порождает
по токену, используя кеш. Разделение времени на эти фазы здесь не измерялось. KV-cache занимает память
пропорционально числу активных последовательностей и их длине, поэтому параллельность ограничена
памятью. Последовательный сервис Transformers ничего не говорит о скорости SGLang/vLLM: у них пакетная
обработка, страничный KV-cache и повторное использование префиксов, а здесь этого нет и они не запускались.

9. Опыт A → B → A на STUB (evidence/experiments.log, раздел 5)
  Старт на A: model_id fixture-A.
  Публикация B в другом процессе, без перезапуска: fixture-A, ответ тоже A; указатель уже B.
  Перезапуск: fixture-B. lab.py rollback --to fixture-A и перезапуск: fixture-A.
  Журнал: publish A, publish B, rollback A. Откат заново проверяет файлы и сохранённое решение.
Сбой между указателем и журналом (раздел 3): после сбоя указатель B, события нет; повтор
дописывает одно событие recovered; следующий повтор ALREADY_PUBLISHED. Событий B ровно одно.
Настоящий smoke выполнен отдельно (п. 7). Второй допущенной настоящей версии нет: смена версии
на настоящей модели не показана. Показана загрузка текущего manifest после перезапуска.
Сценарий смены: кандидат проходит gate → lab.py run --role candidate → перезапуск API → /ready
показывает новый model_id. Откат: lab.py rollback --to <model_id> и перезапуск API.

10. Ограничения
Golden 56 примеров: это небольшая выборка, и она использовалась при разработке, независимым аудитом
не является. Замер 8+8 запросов одного типа с короткими ответами на CPU ноутбука; память и фазы
генерации не измерялись. Один писатель: конкуренция при публикации не решается.
model-pins.json для adapter зафиксирован по файлам из MLflow в момент этой работы: подмену в MLflow
до этого момента он не обнаружит. Хеши базы сверены с контентными адресами кеша HF.
Кеш HF создан в WSL, его симлинки Windows не читает, поэтому на Windows собран снимок из жёстких
ссылок на те же blob-файлы (scripts/link_base_snapshot.py).
Интеграционный прогон занимает около 5 минут: Prefect поднимает временный сервер в каждом процессе.
Веса, .venv и рабочие каталоги в Git не входят. Для доступа к артефактам нужны кеш Qwen3-0.6B этой
ревизии (публичная модель) и MLflow ДЗ 6+7 для adapter. Проверить решение можно без них: журналы,
манифесты и отчёты лежат в evidence/real/release/.
